# Speculative Decoding — Modified Rejection Sampling & the Bandwidth Arithmetic Behind "Free" Verification

Autoregressive decoding is memory-bandwidth bound, not compute bound — the same bottleneck behind KV-caching and quantization. Generating one token means reading every single weight of the model from HBM into the GPU's compute cores, doing a tiny amount of matrix math relative to that transfer, then throwing all of it away and doing it again for the next token. Speculative decoding is the first technique that exploits this directly: since the GPU is *waiting on memory, not out of compute*, you can verify several tokens in the time it takes to generate one — for free — as long as the math guarantees you still get exactly the target model's output distribution.

---

## 1. Why This Is Possible: The Roofline Argument

For batch size 1, single-token decoding, arithmetic intensity (FLOPs per byte moved from HBM) is very low. A 7B-parameter model in FP16 requires ~14GB to be streamed from HBM per token generated, but the actual compute for a single token's forward pass is minuscule next to the GPU's peak FLOPs. The GPU sits idle waiting on the memory bus.

The key insight: that same weight-streaming cost is paid whether you compute logits for **1** token position or **K** token positions in parallel, because the bottleneck is reading the weights once — not how many positions you multiply them against. A forward pass over a sequence of $K$ already-known draft tokens costs roughly the same wall-clock time as a forward pass over 1 token, right up until $K$ grows large enough to become compute-bound instead.

Speculative decoding weaponizes this asymmetry: use a small, cheap **draft model** $M_q$ to autoregressively guess $K$ tokens ahead, then verify all $K$ guesses in a *single* parallel forward pass of the expensive **target model** $M_p$.

## 2. The Draft-Then-Verify Loop

1. Draft model $M_q$ generates $K$ candidate tokens $x_1, \dots, x_K$ autoregressively, each from $q(x_i \mid \text{prefix}, x_{<i})$.
2. Target model $M_p$ runs **one** forward pass over the prefix plus all $K$ draft tokens simultaneously (this is legal because they're already generated, not being predicted), producing $p(x_i \mid \text{prefix}, x_{<i})$ at every position.
3. Walk left to right through the $K$ positions, deciding whether to **accept** each draft token using the acceptance criterion below. The first rejection stops the walk.
4. Whatever gets accepted (0 to $K$ tokens) plus one bonus/correction token from the target's own distribution becomes the output of this iteration. Repeat.

## 3. The Acceptance Criterion (Modified Rejection Sampling)

For each draft token $x$ sampled from $q(x \mid c)$ at context $c$, with the target's probability $p(x \mid c)$ now known from the parallel verification pass:

$$
\text{accept } x \text{ with probability } \min\left(1, \frac{p(x \mid c)}{q(x \mid c)}\right)
$$

If rejected, **don't just drop the token** — resample a replacement from the residual distribution:

$$
p_{\text{res}}(x) = \frac{\max(0,\; p(x \mid c) - q(x \mid c))}{\sum_{y} \max(0,\; p(y \mid c) - q(y \mid c))}
$$

Intuitively: draft tokens the target model finds *more* likely than the draft model did are always accepted. Draft tokens the target model finds *less* likely get rejected proportionally to how much the draft over-weighted them, and the residual distribution siphons off exactly the probability mass the draft model was "missing."

### Proof this is exact (not an approximation)

The probability the final output token equals $x$ is the sum of two events — direct acceptance, or rejection-then-resample landing on $x$:

$$
P(\text{output}=x) = \underbrace{q(x)\min\!\left(1,\frac{p(x)}{q(x)}\right)}_{\text{accepted directly}} + \underbrace{\left(\sum_{x'} q(x')\left(1-\min\!\left(1,\frac{p(x')}{q(x')}\right)\right)\right)}_{\beta,\ \text{total rejection mass}} \cdot\ p_{\text{res}}(x)
$$

The first term simplifies to $\min(p(x), q(x))$. The rejection mass $\beta = \sum_{x'} \max(0, q(x')-p(x'))$ — and because $p$ and $q$ are both normalized distributions ($\sum p = \sum q = 1$), this quantity is exactly equal to $\sum_{x} \max(0, p(x)-q(x))$, which is precisely the normalizing constant of $p_{\text{res}}$. So the second term collapses to $\max(0, p(x) - q(x))$, and:

$$
P(\text{output}=x) = \min(p(x), q(x)) + \max(0, p(x) - q(x)) = p(x)
$$

The algorithm samples from the exact target distribution $p$, regardless of how bad the draft model $q$ is — a weak draft model only hurts *speed*, never *correctness*.

## 4. Acceptance Rate and Expected Tokens per Iteration

The per-token acceptance rate, averaged over the draft's own sampling, has a clean closed form:

$$
\alpha = \mathbb{E}_{x \sim q}\left[\min\left(1, \frac{p(x)}{q(x)}\right)\right] = \sum_x \min(p(x), q(x)) = 1 - \|p - q\|_{TV}
$$

$\alpha$ is exactly one minus the total variation distance between the draft and target distributions — the better the draft model approximates the target at that position, the higher $\alpha$, the more tokens survive verification.

For a block of $K$ draft tokens (treating $\alpha$ as roughly constant across positions, a simplification), the expected number of tokens emitted per iteration — accepted tokens plus the guaranteed bonus token — is:

$$
\mathbb{E}[\text{tokens per iteration}] = \sum_{i=0}^{K} \alpha^{i} = \frac{1 - \alpha^{K+1}}{1 - \alpha}
$$

## 5. Where the Memory Bandwidth Savings Actually Come From

Standard decoding of $N$ tokens streams the full target model's weights from HBM $N$ separate times — one full weight-read per token, since decoding is inherently serial.

Speculative decoding restructures that same $N$-token generation into iterations of roughly $(1-\alpha^{K+1})/(1-\alpha)$ tokens each, where each iteration costs:

* **1** parallel target-model forward pass (1 full weight-read of $M_p$ — expensive, but amortized over multiple output tokens instead of just one)
* **$K$** serial draft-model forward passes (each a weight-read of $M_q$, typically 10–20x smaller than $M_p$, so cheap even done $K$ times)

Total bytes streamed from HBM for one iteration: $\text{bytes}(M_p) + K \cdot \text{bytes}(M_q)$ — versus standard decoding's $(\text{tokens produced}) \times \text{bytes}(M_p)$ for the same output length. When $\text{bytes}(M_q) \ll \text{bytes}(M_p)$, the dominant cost of $N$ tokens collapses from $N$ full-model reads down to roughly $N / \mathbb{E}[\text{tokens per iteration}]$ full-model reads — the same weight tensor gets reused across multiple output tokens per HBM trip instead of being re-fetched for each one.

## 6. Speedup Formula and the Latency Payoff

Let $c = T_{\text{draft}} / T_{\text{target}}$ be the relative per-forward-pass cost of the draft model (small, since it has far fewer parameters — $c$ is often in the 0.05–0.15 range). Time for one speculative iteration:

$$
T_{\text{iter}} \approx K \cdot c \cdot T_{\text{target}} + T_{\text{target}}
$$

(the $+T_{\text{target}}$ term is the single parallel verification pass, which costs about the same as one normal decode step thanks to the roofline argument in §1). Combined with the expected tokens per iteration, the wall-clock speedup over standard decoding is:

$$
\text{Speedup} = \frac{1 - \alpha^{K+1}}{(1-\alpha)(1 + Kc)}
$$

This is why speculative decoding is a **latency** win specifically, not just a FLOPs accounting trick: because verification of $K$ tokens costs roughly the same wall time as generating 1 token normally, every additional accepted token in the block is very close to *pure* latency reduction — not a proportional trade against more compute.

## 7. Where It Breaks Down

* **$K$ too large:** verifying more positions eventually raises arithmetic intensity enough to shift the target-model pass from memory-bound to compute-bound, and the "verification is basically free" assumption in §1 stops holding.
* **Low $\alpha$:** a draft model poorly aligned with the target (different tokenizer behavior, very different training data/style) rejects early and often — the block collapses to 1 token per iteration, and the draft model's own cost becomes pure overhead with no bandwidth payoff.
* **Draft model quality vs. size trade-off:** a bigger, better-aligned draft model raises $\alpha$ but also raises $c$ — there's an optimum $K$ (and an optimum draft model size) where marginal expected gain $\alpha^K$ roughly balances marginal cost $c$.

## 8. Beyond a Single Draft Chain: Tree-Based Speculation

Techniques like Medusa and EAGLE extend this from a single linear chain of $K$ guesses to a **tree** of candidate continuations verified in one target pass, using multiple lightweight prediction heads instead of a full second model. Because $\alpha^{K+1}$ decays fast for a linear chain, branching into a tree raises the expected number of accepted tokens per verification pass without paying for a separate draft model's serial forward passes at all — the tradeoff shifts from "cheap serial draft model" to "wider single verification pass with more candidate branches."

## Comparison

| | Standard Decoding | Speculative Decoding (linear) | Tree-Based (Medusa / EAGLE) |
| :--- | :--- | :--- | :--- |
| HBM reads per output token | 1 full $M_p$ read | Amortized: $\approx 1/\mathbb{E}[\text{tokens/iter}]$ | Amortized further via wider trees |
| Output distribution | Exact $p$ | Exact $p$ (proven, §3) | Exact $p$ (same rejection-sampling core) |
| Extra model needed | None | Separate draft model $M_q$ | Lightweight heads on $M_p$ itself |
| Bottleneck risk | Always memory-bound | Breaks down if $K$ pushes pass compute-bound | Same, bounded by tree width |
| Speedup driver | N/A | $\alpha$ (draft/target agreement) | Branch coverage per verification pass |

## Key Engineering Takeaway

> Speculative decoding isn't a compute optimization — it's a scheduling trick against a hardware constraint. The exactness proof in §3 is what makes it safe to ship: correctness never depends on the draft model being good, only speed does. Every memory-bandwidth-bound decode step in an LLM pipeline is implicitly begging to have its idle compute filled with speculative work — this is the same principle as batching independent requests together, just applied to a single sequence's own future tokens instead of across users.
