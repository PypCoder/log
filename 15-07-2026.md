# Zero-Copy Serialization — FlatBuffers, Cap'n Proto & The Hidden Cost of Parsing

The bottleneck in most high-throughput data systems isn't the network anymore — links are fast and CPUs are faster than the code that's supposed to keep them fed. What actually eats the CPU budget is the invisible tax between "bytes arrived" and "data I can use": tokenizing, allocating, and copying just to turn a byte buffer into objects you can touch. FlatBuffers and Cap'n Proto exist because someone asked a simple question — what if that tax was zero?

---

## 1. The Parse-Then-Allocate Model (What JSON and Protobuf Actually Cost)

JSON deserialization is a two-phase job: tokenize the text (scan for `{`, `"`, digits, escape sequences), then build a tree of dynamically-typed heap objects from those tokens. Every string needs its own heap allocation (or at minimum a copy, since JSON strings must be unescaped before use), every nested object or array allocates a container, and in dynamically-typed runtimes even numbers get boxed onto the heap. Critically, this cost scales with the *entire* message: to read field 40 of a 40-field object, you still tokenized and allocated all 40.

Protobuf improves on this — binary encoding means no text scanning, and the schema is known ahead of time so field tags decode via cheap varint math instead of string matching. But the decode step still walks the whole byte stream and constructs a native heap object graph: message classes, repeated fields as vectors, strings copied into heap-owned buffers. It's faster than JSON, but it's still $O(n)$ in message size and still allocates roughly one object per field or repeated element.

Google has publicly acknowledged that some of its production servers spend on the order of a third of their CPU time just encoding and decoding Protobuf messages, while the network interface sits mostly idle. That's the tell: the bottleneck had already moved from wire bandwidth to CPU-bound allocate-and-copy work, years before FlatBuffers or Cap'n Proto existed to fix it.

## 2. Zero-Copy's Core Idea: The Wire Format *Is* the Memory Layout

Both FlatBuffers and Cap'n Proto make the same architectural bet: define the byte layout on the wire to already match what a compiler would generate for a native struct — fixed widths, fixed offsets, correct alignment for the target CPU. Once the buffer exists in memory (from a `recv()`, an `mmap()`'d file, or a shared-memory segment), reading field $N$ is just offset arithmetic and a cast. There is no walk over the whole structure, no allocation, and no copy — the "parse" step is deleted, not optimized.

This changes the cost model entirely. Access to any single field after decode in JSON/Protobuf is preceded by an unavoidable $O(n)$ decode over the *whole* message. Zero-copy field access is $O(1)$ per field, full stop — because the thing you'd normally call "the decoded object" and "the wire bytes" are the same memory.

Cap'n Proto pushes this to its logical extreme: if your application builds its message directly in Cap'n Proto's arena format using its own API (rather than building native objects and converting at the end), there is no separate serialize step *at all*. "Serializing" a message is just writing bytes you already had to a socket or a file. This is the origin of Cap'n Proto's own benchmark claim of being infinitely faster than Protobuf — by its own admission, an intentionally unfair number, because it only measures in-memory encode/decode time, and that time is genuinely zero when there's no encode/decode step to perform.

## 3. FlatBuffers' Vtable vs. Cap'n Proto's Direct Layout

The two formats reach zero-copy access through different structural trade-offs:

* **FlatBuffers uses per-object vtables.** Every table stores a signed offset back to a vtable, and the vtable stores a byte offset for each schema field. If a field's vtable slot is out of range or zero, the field is simply absent and a default is returned — this is what lets fields be optional and schemas evolve without wasting space on unset values. Vtables with identical field-presence patterns are deduplicated across objects, so the overhead amortizes well when you have many similar records. The cost: every field read is one extra indirection — offset into vtable, then offset into data.
* **Cap'n Proto skips vtables entirely.** Every field gets a fixed slot in the struct's data section regardless of whether it's set; "unset" is represented by XOR-ing against the field's default so an all-zero region reads back as the default value. Reads become pure direct-offset access — one less indirection than FlatBuffers — at the cost of wasted space: unset optional fields still occupy their full width as zero bytes. Cap'n Proto claws that space back with an optional "packing" pass, a tight loop that strips runs of zero bytes before transmission, applied only when bandwidth actually matters.

In short: FlatBuffers spends one indirection to buy compact wire size and flexible schema evolution; Cap'n Proto spends wire-size padding to buy the simplest possible field access, with packing as an opt-in fix for the size cost.

### A minimal zero-copy reader, by hand

Stripped of vtables and schema evolution, this is the mechanism both formats are built on — reading a field is offset math over a buffer you already own, not a parse:

```rust
// A zero-copy "view" over a byte buffer that could have arrived straight
// from a socket recv() or an mmap'd file — no parsing, no heap allocation.
struct PlayerView<'a> {
    buf: &'a [u8],
}

impl<'a> PlayerView<'a> {
    // health lives at byte offset 0 as a little-endian u32.
    fn health(&self) -> u32 {
        u32::from_le_bytes(self.buf[0..4].try_into().unwrap())
    }

    // name is length-prefixed starting at offset 4: [u16 len][utf8 bytes...].
    // Returns a &str borrowed from the original buffer — not a new String.
    fn name(&self) -> &'a str {
        let len = u16::from_le_bytes(self.buf[4..6].try_into().unwrap()) as usize;
        std::str::from_utf8(&self.buf[6..6 + len]).unwrap()
    }
}

fn main() {
    let wire_bytes: &[u8] = &[100, 0, 0, 0, 5, 0, b'A', b'l', b'i', b'c', b'e'];
    let player = PlayerView { buf: wire_bytes };

    // No .parse(), no JSON tree, no heap allocation for `name` — just offsets.
    println!("health = {}, name = {}", player.health(), player.name());
}
```

`name()` hands back a borrow into the original buffer with the same lifetime — the defining trait of zero-copy: nothing new was allocated to make the field readable. Real FlatBuffers/Cap'n Proto generated accessors do the same thing, plus the vtable/direct-offset indirection above, plus bounds-checking (more on that below).

## 4. Memory Allocation Overhead — Where the Cost Actually Hides

The cost of a single heap allocation isn't just the `malloc` call itself — that's tens of nanoseconds under a healthy allocator, more under contention or fragmentation. The deeper cost is what allocation does to memory *layout*. A JSON-parsed object tree is scattered: every string and nested object lives wherever the allocator happened to place it, often far from its parent or siblings. Walking that tree later means chasing pointers across cold cache lines — cache misses that routinely dwarf the actual computation being performed.

A zero-copy buffer is a single contiguous region — or in the `mmap`/shared-memory case, not even an allocation at all, just memory another process or the OS already handed you. Reading adjacent fields is sequential, cache-friendly access, the same principle that makes array-of-structs iteration beat linked-list traversal.

In garbage-collected languages this compounds further: every heap object a JSON parse produces is garbage the collector must eventually trace and reclaim. A service parsing thousands of JSON messages per second accumulates GC pressure that shows up as tail-latency spikes — invisible in a microbenchmark of "how fast does parse() return," very visible in p99 latency under real load. Zero-copy reads don't allocate, so there's nothing for the collector to track.

Meta's Android engineering team measured this directly after moving their app's client-server object model to FlatBuffers: transient memory allocations dropped by roughly 75%, story load time from the disk cache fell from about 35ms to 4ms, and cold start improved 10–15%. None of that came from a faster parser — it came from not having a parser at all.

## 5. Serialization Cost — The Write Side

* **JSON encode:** format every number to decimal text (non-trivial work, especially for floats via itoa/dtoa-style algorithms), escape every string for quotes and control characters, and grow an output buffer that reallocates and copies as it doubles in capacity. All of this exists purely because text is the wire format — none of it touches the actual data being represented.
* **FlatBuffers encode:** a builder writes fields as raw bytes into a buffer — by design, built back-to-front to minimize bookkeeping — computing vtable offsets as it goes. No text formatting, no escaping, no buffer-growth-and-copy pattern.
* **Cap'n Proto encode:** if the application builds its message directly through Cap'n Proto's arena API instead of building native objects and converting afterward, there's no distinct "serialize" pass at all. Sending the message is handing those already-correct bytes to a socket write or a file.

## 6. System Throughput Impact

The headline effect: parse cost that used to scale $O(n)$ with message size collapses to near-$O(1)$ per field actually touched. That matters disproportionately for large messages where consumers only need a handful of fields — a logging pipeline routing on two header fields out of a large record, a game engine streaming terrain data where a frame only touches nearby geometry, a market-data consumer that only reads price and size out of a much larger tick.

This is exactly why high-frequency trading and market-data systems lean on zero-copy formats (Cap'n Proto, FlatBuffers, SBE): at hundreds of thousands of messages per second, any allocation or encode/decode step blows the latency budget outright. Shared-memory IPC between co-located processes is the case where the "infinity times faster" claim is least unfair — the raw buffer crosses a shared-memory ring with zero copies in either direction. In real network transmission the gap narrows considerably: Cap'n Proto's own benchmarking found packed messages over a local pipe running around 30% faster than Protobuf, not infinitely faster — the dramatic number measures a specific, narrow thing (transform cost), not overall transmission cost.

Worth naming the parallel explicitly: this is the same philosophy as `sendfile()`/`mmap()` zero-copy I/O at the OS level — avoid materializing an intermediate copy of data you're about to hand off unchanged. Zero-copy serialization is that same idea, moved up one layer into the wire format itself.

**Honest caveat:** zero-copy formats generally lose on raw wire size — FlatBuffers' vtable overhead and Cap'n Proto's zero-padding for unset fields both cost bytes that a tightly-packed Protobuf message wouldn't spend. If a system is bandwidth-bound rather than CPU-bound (the public internet, rather than a datacenter LAN or shared memory), that calculus can flip — compression, or plain Protobuf, may still win.

**Security caveat, since this crosses a trust boundary:** reading directly from a buffer is not the same as trusting it. If an offset in an untrusted message points outside the buffer, dereferencing it must not corrupt memory or leak adjacent bytes. Both formats' generated accessors bounds-check every offset before following it — an out-of-range vtable entry returns a default rather than segfaulting. That bounds-check is the one "parse-like" cost that survives zero-copy design, and it's non-optional the moment the buffer crosses a process or network boundary rather than being entirely self-generated.

## Comparison

| | JSON | Protobuf | FlatBuffers | Cap'n Proto |
| :--- | :--- | :--- | :--- | :--- |
| Wire format | Text | Binary, varint-tagged | Binary, offset-based tables | Binary, fixed-offset structs |
| Parse step before use? | Yes — tokenize + tree build | Yes — decode to native objects | No — read directly from buffer | No — read directly from buffer |
| Allocations to read a message | $O(\text{fields} + \text{nested objects})$ | $O(\text{fields} + \text{nested objects})$ | Zero — buffer *is* the object | Zero — buffer *is* the object |
| Field access after decode | Hash/tree lookup | Direct member access | Offset → vtable → offset | Direct offset access |
| Typical wire size | Largest (text + repeated keys) | Compact | Larger than Protobuf (vtables + padding) | Larger unpacked; comparable once packed |
| Schema evolution | N/A | Strong (field numbers) | Strong (vtable defaults) | Strong (fields fixed at end of struct) |
| Best fit | Human-editable configs, public APIs | General RPC, bandwidth-constrained links | Game engines, mobile apps, mmap'd assets | Shared-memory IPC, ultra-low-latency RPC |

## Key Engineering Takeaway

> The performance win here was never "faster parsing" — it's that there's no parsing step left to be fast or slow. Every allocation removed from a hot path removes not just its own cost but the cache-miss and GC-pressure tax that everything downstream of it would otherwise pay. The same logic scales up a layer: an API serving ESM2 embeddings or a protein contact map as a raw, offset-addressable buffer instead of JSON-encoding every float skips exactly this tax — the client reads the array straight out of the response body instead of allocating a JS object graph one float at a time.
